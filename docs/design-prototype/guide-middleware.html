Middleware

Wrap every task with cross-cutting logic — logging, tracing, auth, metrics — through six composable hooks with stack semantics.

Overview

A middleware is an object that implements one or more of six hooks. The worker composes them into a stack: hooks wrap task execution in entry/exit order, similar to WSGI or ASGI middleware.

Note Middleware runs on the worker, not the client. The pre_enqueue and post_enqueue hooks run in the client process but all four execution hooks are worker-side.

The six hooks

Hook Where When
pre_enqueueClientBefore the message is published to RabbitMQ.
post_enqueueClientAfter the broker confirms the publish.
pre_executeWorkerAfter delivery, before run().
post_executeWorkerAfter run() succeeds, before ack.
on_errorWorkerWhen run() raises, before retry decision.
on_retryWorkerWhen a retry is scheduled.

Writing a middleware

Subclass Middleware and override only the hooks you need. Unmentioned hooks are no-ops. The first argument is always a TaskContext — it carries the task, its arguments, the delivery metadata, and mutable state.

middleware/timing.py 
import time, logging
from swarmq.middleware import Middleware, TaskContext

log = logging.getLogger("swarmq.timing")


class TimingMiddleware(Middleware):
    async def pre_execute(self, ctx: TaskContext) -> None:
        ctx.state["t0"] = time.perf_counter()

    async def post_execute(self, ctx: TaskContext, result: object) -> None:
        elapsed = time.perf_counter() - ctx.state["t0"]
        log.info("task=%s elapsed=%.3fs", ctx.task_name, elapsed)

    async def on_error(self, ctx: TaskContext, exc: Exception) -> None:
        elapsed = time.perf_counter() - ctx.state.get("t0", time.perf_counter())
        log.warning("task=%s failed=%.3fs err=%r", ctx.task_name, elapsed, exc)

Registration

Middleware are registered in order on the SwarmQ app. Execution hooks run in the order registered; exit hooks (post_execute, etc.) run in reverse — the same nesting you know from WSGI.

app.py 
app = SwarmQ(
    broker_url=BROKER_URL,
    backend_url=BACKEND_URL,
    middleware=[
        TracingMiddleware(),   # outermost
        TimingMiddleware(),
        AuthContextMiddleware(),  # innermost, wraps run()
    ],
)

Execution order

Given three middleware registered as [A, B, C] around a task body, the call graph looks like this:

flow 
A.pre_execute  →  B.pre_execute  →  C.pre_execute
                                        ↓
                                    run(task)
                                        ↓
C.post_execute ←  B.post_execute ←  A.post_execute
Careful Exceptions raised inside a middleware hook abort the chain and surface as task errors. Use on_error to record or transform them — don't swallow them silently.

The TaskContext

Every hook receives the same TaskContext instance for a given execution, so middleware can share state via ctx.state. Frequently used fields:

FieldTypeDescription
task_namestrRegistered task name (from TaskInfo.name).
args, kwargstuple, dictArguments passed to schedule().
message_idstrUnique ID assigned at enqueue time.
retry_countintHow many previous attempts this message has had.
statedictMutable per-execution scratch space. Lives only for one invocation.
