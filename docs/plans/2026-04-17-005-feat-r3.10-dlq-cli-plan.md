# feat: R3.10 — DLQ-CLI

## Overview

Vervollständigt die Phase-3-CLI um vier `swarmq dlq`-Subcommands für
Operator-Sichtbarkeit und Recovery der DLQ-Messages:

- `swarmq dlq list [--queue Q] [--limit N] [--format ...]`
- `swarmq dlq inspect <task_id> [--queue Q] [--scan-limit N]`
- `swarmq dlq retry <task_id> [--queue Q]`
- `swarmq dlq retry --all [--queue Q] [--limit N]`
- `swarmq dlq purge [--queue Q]`

Identifier für inspect/retry ist der `task_id` aus dem JSON-Payload
(`payload.task.id`). RabbitMQ vergibt keine stable intrinsische
Message-ID für gedeadletterte Messages; der User-sichtbare Bezug ist
der Task.

## Problem Frame

Phase 2 etablierte die 3-Queue-Topologie (`{queue}`, `{queue}.DQ`,
`{queue}.XQ`). Tasks erreichen die XQ via:
- Retry-exhausted (`_evaluate_retry` → `_send_to_dlq`)
- NoRetry-Exception (`_evaluate_retry` direkt)
- retry_exceptions-Filter-Miss (`_evaluate_retry`)
- Lock-render-fail / empty-render (R3.4)
- Lock-conflict-cap (R3.4)

Bisher fehlt der Operator-Pfad: keine Möglichkeit, DLQ-Inhalt zu
sehen, einzelne Messages zurück in die Main-Queue zu schieben oder
die DLQ zu leeren. Workarounds über RabbitMQ-Management-UI sind
möglich, hängen aber von der optionalen Management-Extension ab
und erfordern Kontextwechsel.

## Requirements Trace

- **R1. `swarmq dlq list`** — enumerate DLQ messages non-destructively.
  Columns: task_id, task_name, retry-count, traceback-preview, body-size.
  Scoped by `--queue`. (aufgabe.md §11.2)
- **R2. `swarmq dlq inspect <task_id>`** — full payload + all headers
  für einen Task. Zeigt Traceback, Original-Args/Kwargs, Retry-Count,
  Unique-Header. (aufgabe.md §11.2)
- **R3. `swarmq dlq retry <task_id>`** — Republish in `{queue}`. Reset
  `x-swarmq-retry-count`-Header damit der Task wieder den vollen
  Retry-Budget bekommt. (aufgabe.md §11.2)
- **R4. `swarmq dlq retry --all`** — Republish aller DLQ-Messages.
  Sicherheits-Cap `--limit` (default 10000). (aufgabe.md §11.2)
- **R5. `swarmq dlq purge`** — Native `queue.purge()` auf XQ. (aufgabe.md §11.2)
- **R6. JSON-Output** — Alle Subcommands unterstützen `--format json`
  für agent/script-konsumierbare Ausgabe.
- **R7. Broker-Only** — CLI spricht nur mit RabbitMQ (SWARMQ_BROKER_URL).
  Kein Valkey-Backend notwendig.

### Key Technical Decisions

- **task_id als Message-Identifier:** RabbitMQ hat keine stabile
  intrinsische ID für DLQ-Messages. `delivery_tag` ändert sich bei
  jedem `basic.get`. Der User-sichtbare Bezug ist `task_id` aus dem
  Payload (`{"task": {"id": "..."}}`). Implikation: CLI muss den
  Body parsen um task_id zu extrahieren. Malformed-Body-Entries
  (unparseable JSON) erscheinen in `list` mit `task_id=None` und
  sind nicht via `inspect <task_id>` erreichbar — nur via
  `retry --all` oder `purge` bedienbar.
- **Drain-and-republish statt nack-requeue:** `basic.nack(requeue=True)`
  legt Messages am KOPF der Queue zurück. Ein Read-Loop mit
  get+nack(requeue=True) iteriert daher ewig auf derselben Message.
  Korrekte Semantik: destruktiv drainen (`no_ack=True`), in
  `finally` zurückpublishen (außer bei retry/purge wo das nicht
  gewollt ist).
  Trade-off: Crash während des Drain-and-republish-Zyklus verliert
  gerade-gelesene-noch-nicht-republished Messages. Akzeptabel für
  Operator-Inspection-Tool; Produktions-Recovery sollte `retry --all`
  oder `purge` bevorzugen (einmaliger Transfer, kein Round-Trip).
- **Retry-Count-Reset:** `retry` und `retry --all` entfernen
  `x-swarmq-retry-count` aus dem Header, damit der Task den vollen
  Retry-Budget auf dem Redelivery bekommt. Operator-Intent:
  "nochmal versuchen". Original-Traceback-Header bleibt, damit das
  erste Fail-Event im redelivered Message sichtbar bleibt.
- **Queue-Type-Agnostik:** Die Broker-Methoden nutzen keine
  queue-type-spezifischen Features. Klassische und Quorum-Queues
  funktionieren identisch.
- **No passive-declare:** Die CLI nutzt `get_queue()` ohne passive-
  Flag. Wenn die DLQ nicht existiert, schließt aio_pika den Channel
  mit einem klaren Fehler. Der alternative Weg (passive declare)
  hätte denselben Effekt; get_queue liest sich simpler.

### External References

Keine — rein RabbitMQ/aio-pika-Standardfunktionen.

## Open Questions

### Resolved During Planning

- **Identifier:** task_id (nicht delivery_tag, nicht custom UUID).
- **Retry-Count:** Reset beim Retry (Operator-Intent).
- **Mutex-Semantik:** Keine (zwei Operatoren können parallel
  `dlq list` aufrufen; drain+republish gibt lebendige Queue-State,
  nicht Snapshot-Konsistenz).
- **--queue Default:** `default` (gleiches default wie
  `--queues default` in `swarmq worker`).

### Deferred to Implementation

- **Exact error message wenn Queue nicht existiert:** aio_pika
  wirft je nach channel-state unterschiedlich; Tests pinnen.
- **Ordering-Garantien bei list:** drain+republish ändert
  Message-Order. Tests dokumentieren dass Reihenfolge nicht
  stabil ist (akzeptierte Operator-Tool-Einschränkung).

## Implementation Units

- [x] **Unit 1: RabbitMQBroker DLQ-Primitives**

**Goal:** Fünf Broker-Methoden als Foundation für die CLI-Handler.

**Requirements:** R1, R2, R3, R4, R5.

**Dependencies:** Keine (additive Broker-API).

**Files:**
- Modify: `src/swarmq/broker/rabbitmq.py`
- Test: `tests/integration/broker/test_rabbitmq_dlq.py` (neu)

**Approach:**
- `_extract_task_id(body: bytes) -> str | None` — JSON-parse mit
  try/except, None bei Malformed.
- `_drain_dlq_with_filter(queue_name, limit, match_task_id=None,
  move_to_main=False) -> tuple[list[dict], list[dict]]` —
  destruktives drain via `get(no_ack=True)`, finally-republish
  mit task_id-Filter. Entries enthalten task_id, task_name, queue,
  headers, body, body_raw, body_size.
- `list_dead_letter_queue(queue_name, limit=100)` — nutzt drain
  ohne Filter/Move, gibt gekürzte Liste zurück.
- `inspect_dead_letter_message(queue_name, task_id, scan_limit=1000)`
  — drain mit task_id-Filter, erste Match wird returned.
- `retry_dead_letter_message(queue_name, task_id, scan_limit=1000)`
  — drain mit Match + move_to_main=True, Rest republishen in DLQ.
  Returns bool (found or not).
- `retry_all_dead_letter_messages(queue_name, limit=10000)` — drain
  ohne Filter, alle direkt in Main. Returns int (moved count).
- `purge_dead_letter_queue(queue_name)` — native `queue.purge()`,
  returns message_count.

**Patterns to follow:**
- `publish_to_dead_letter_queue` (rabbitmq.py:86) Publish-Pattern.
- aio_pika `queue.get(no_ack=True, fail=False)` + `queue.purge()`.

**Test scenarios:**
- Happy path: publish 3 Messages in DLQ, list returned 3 Einträge,
  DLQ bleibt mit 3 Einträgen nach Call.
- Happy path: inspect matching task_id returns full dict.
- Happy path: inspect non-matching task_id returns None.
- Happy path: retry matching moves zu Main-Queue, DLQ size
  decremented by 1.
- Happy path: retry --all moves alle, DLQ empty.
- Happy path: purge leert DLQ komplett.
- Edge case: malformed body (non-JSON) in DLQ → list zeigt
  task_id=None, inspect findet nicht.
- Edge case: empty DLQ → list returns [], retry_all returns 0,
  purge returns 0.
- Edge case: retry reset x-swarmq-retry-count header
  (checked auf Main-Queue empfangener Message).

grün gegen Dev-Stack.

nicht offensichtlich (nack=True Endlosschleife); Tests pinnen das

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| drain-and-republish verliert Messages bei CLI-Crash mid-drain | Dokumentiert im Docstring; Operator-Empfehlung: `retry --all` oder `purge` für Produktions-Recovery (einmaliger Transfer statt Round-Trip). |
| task_id-basierte Identifikation versagt bei Malformed-JSON-Bodies | list zeigt task_id=None — Operator sieht Problemfall; purge als Fallback-Recovery. |
| nack(requeue=True) Endlosschleife bei naivem Read-Loop | Drain-and-republish-Pattern ist die Lösung; Tests pinnen es. |
| Retry-Count-Reset re-aktiviert Task mit full budget → Fail-Storm wenn Bug systematisch | Operator-Verantwortung dokumentiert; Alternative (preserve count) kann später per Flag ergänzt werden (YAGNI v1). |
| Queue nicht deklariert → aio_pika-Channel-Close-Error | CLI rendert Error als `swarmq dlq list: <reason>`; Exit-Code 1. Dokumentiert. |
