## 3. Versionssprung, Build, Tag (nach F1–F4)

1. Nach dem Merge auf `main` einen Branch `release/0.12.0rc1` anlegen.
2. `pyproject.toml`: `version = "0.12.0rc1"`.
3. `uv lock` (Lockfile auf die neue Version; danach `git diff uv.lock`
   prüfen, dass sich nur der swarmq-Eintrag ändert).
4. Spec neu erzeugen: `uv run python -m swarmq.agent_spec` (schreibt
   `website/reference/agent/spec/index.json` mit `swarmq_version`).
   Danach `uv run --extra test --extra reload pytest
   tests/unit/test_agent_spec.py` grün.
5. Changelog EN/DE: Überschrift `## [Unreleased]` in
   `## [0.12.0rc1] — <Datum>` umbenennen (oder einen RC-Abschnitt mit
   Verweis auf den Inhalt darunter), den Satz „0.12.0, not yet
   released“ / „noch unveröffentlicht“ anpassen.
6. Gates, jedes Ergebnis ausdrücklich prüfen (`set -o pipefail`,
   Exit-Code):
   - Unit: `uv run --extra test --extra reload pytest tests/unit`
   - Integration und e2e über den Wrapper, zusätzlich gegen RabbitMQ
     4.2.9 (`SWARMQ_TEST_RABBITMQ42_PORT=5742`,
     `SWARMQ_TEST_RABBITMQ42_MGMT_PORT=15742`)
   - compat (`-m compat`, Basis 0.11.1), Chaos
   - `uv run mypy src`, `ruff check`/`ruff format --check` der
     geänderten Dateien
   - `uv run --extra docs mkdocs build --strict`
   - Golden-Dateien unverändert (`git status tests/` sauber)
7. `uv build`; Wheel prüfen: Lua-Skripte (`lock_extend.lua` neu),
   `py.typed`, keine Testdateien; `pip install dist/*.whl` in einem
   frischen venv mit Python 3.14, `swarmq --version` zeigt `0.12.0rc1`,
   `swarmq check --help` läuft.
8. Commit `chore(release): Version 0.12.0rc1`, Tag `v0.12.0rc1`
   (F2, F3).
9. Upload durch Georg (F4).
10. Hinweis für alle Anleitungen: `pip install 'swarmq==0.12.*'` findet

## 4. Loadsuite, 6 h (nach F5)

Repo `~/Dokumente/Development-Privat/swarmq-loadsuite`, Pin auf
`v0.12.0rc1` (Submodule `vendor/swarmq` und Git-Tag). Lange Läufe nur
losgelöst starten: `setsid nohup uv run loadsuite run … > log 2>&1
< /dev/null &`; Hintergrundbefehle einer Claude-Sitzung enden nach
60 Minuten.

Vorarbeit in der Suite:

- [ ] Konformität (`uv run loadsuite conform`): Register um die fünf
      neuen Signale (`TASK_UNKNOWN_DEFERRED`, `SCHEDULER_FIRE_UNROUTABLE`,
      `SCHEDULER_CRON_UNOWNED`, `SCHEDULER_VALKEY_CHECKED`,
      `SCHEDULER_QUEUE_ORPHANED`) und die neuen Log-Events ergänzen;
      die Zusicherung der Signalzahl anpassen.
- [ ] Docker-Stack: Valkey mit `maxmemory-policy noeviction` und AOF,
      sonst verweigern die Worker den Start (Exit 78). Erst
      `swarmq check` im Stack.
- [ ] Verbindungslimits des Test-RabbitMQ: zwei Verbindungen je
      Worker-Prozess.
- [ ] Grace-Period im Compose-Stack ≥ `SWARMQ_SHUTDOWN_TIMEOUT + 15 s`,
      sonst verfälschen die Fault-Injektionen (Kill, Restart) die
      Messung.

Messgrößen (Vergleich mit dem letzten Referenzlauf am Pin v0.9.0):

| Messgröße | Abbruch / Bewertung |
|---|---|
| Durchsatz (Tasks/s) über 6 h | Stop condition: mehr als 10 % unter der Referenz |
| Verluste | 0 |
| Doppelausführungen | nicht mehr als in der Referenz (1 h: 40 bei Fault-Injektion); jede Doppelausführung einem Fault zuordnen |
| Keyzahl in Valkey | Plateau nach Anlauf; kein lineares Wachstum (Stop condition) |
| Erholungszeit nach Störungen | im Budget wie an v0.9.0 |
| `swarmq_delay_tiers_unavailable`, `queue_dead_letter_at_most_once`, `task_lock_lost` | 0 bzw. erklärt |

Szenario „Semaphor-Überlast“ (neu, Plan R11/MR 13):

- [ ] Ein Task mit `lock=` und `max_concurrency=k` (Semaphor), Last
      deutlich über `k` gleichzeitigen Ausführungen über mindestens 1 h.
- [ ] Beobachten: `swarmq_lock_waits`, `swarmq_lock_wait_oldest_seconds`,
      Rate der Rückstellungen und Valkey-Operationen je Sekunde,
      `task_lock_conflict` (höchstens etwa einmal je Minute und
      Nachricht), keine `LockWaitExceeded` solange Halter leben, keine
      Doppelausführung, Durchsatz der übrigen Queues unverändert.
- [ ] Variante mit gemischten `hard_timeout` unter einem Semaphor-Namen
      nur als Nachweis der dokumentierten Grenze, nicht als Abnahme.

Fehlende Q7-Benchmarks (Hot-Path, kein zusätzlicher Roundtrip je
Nachricht): für MR 10 (Delay-Stufen), MR 12 (Ausführungsidentität) und
MR 13 (Locks) fehlt der Loadsuite-Vergleich vor/nach dem MR.

- [ ] Je MR einen kurzen Benchmark-Lauf am Commit vor dem ersten und
      nach dem letzten Commit des MR (Commits über

- [ ] Ergebnis im Plan unter Q7 nachtragen. Ein Rückgang über 10 % ist

## 5. Staging über 8 Tage (nach F6, F7)

Ziel: die Fristen von 24 h (Prune, Cancel-Flag, Ergebnis-TTL) und
7 Tagen (Rückstands-TTL des Ausführungsschutzes,
`report:queues`, DLQ-Aufbewahrung) mindestens einmal ganz ablaufen
sehen.

Ablauf:

1. Deploy-Leitfaden Schritt 0 bis 5 auf Staging ausführen, mit
   `--pre`. 0.11.1 muss vorher als eigenes Deployment laufen.
2. Mischbetrieb bewusst einplanen: Tag 1 mit mindestens einem
   0.11.1-Worker je Queue (Leaderwechsel in beide Richtungen,
   `scheduler_leader_outdated` erwartet), ab Tag 2 nur 0.12.0rc1.
3. Einen Rollback auf 0.11.1 und zurück üben (Tag 2 oder 3), ohne
   Namensraum.
4. Täglich zur selben Uhrzeit die Keyzahl je KeySpace-Familie
   erfassen (nur lesend, `SCAN` mit `MATCH`, nie `KEYS`, nie gegen
   Produktion ohne Absprache):

   ```bash
   P="${NS:+$NS:}sq:"
   for fam in 'result:*' 'cancel:*' 'unique:*' 'progress:*' 'wf:*' \
              'guard:*' 'lock:*' 'rl:*' 'control:*' 'sched:fired:*' \
              'sched:inflight:*' 'sched:handover:*' '{sched}:*'; do
     n=$(valkey-cli -u "$SWARMQ_BACKEND_URL" --scan --pattern "$P$fam" | wc -l)
     echo "$(date -u +%FT%TZ) $fam $n"
   done >> keyzahl-staging.log
   ```

   Dazu `INFO memory` (`used_memory`, `maxmemory`) und
   `swarmq_valkey_memory_used_ratio`.
5. Erwartung: jede Familie erreicht ein Plateau. `guard:*` darf bis
   Tag 7 steigen (Rückstands-TTL 7 d, bei `max_age` mindestens
   `max_age + 300` s), muss dann abflachen. `{sched}:*` bleibt
   annähernd konstant (`report:queues` verfällt 7 d nach der letzten
   Meldung, `report:known` nur mit der Definition). `sched:handover:*`
   (Marker vor 0.12) verschwindet nach dem Mischbetrieb.
6. Täglich prüfen: `swarmq check` (Exit 0),
   `swarmq_scheduler_queues_orphaned`, `swarmq_supervisor_locked_slots`,
   `swarmq_scheduler_crons_held`, `swarmq_tasks_unknown_deferred_total`,
   DLQ-Tiefen, Broker-Log auf `PRECONDITION_FAILED` (erwartet: bis zu
   zwei je Prozessstart und von 0.12 angelegter Queue).
7. Abschlussbericht: Kurven je Familie, Auffälligkeiten, Entscheidung
   für F8.

## 6. Bekannte Grenzen nach 0.12.0 (Plan Abschnitt 7)

Stehen im Changelog EN/DE unter „Known limits“ und „Takes effect only
when …“; hier zur Abnahme im Staging:

- BZ-02/09/11 wirken erst mit einem Leader ab 0.12; BZ-06/12 voll erst,
  wenn alle Worker 0.12 fahren.
- „Worker vor Producern“ gilt dauerhaft für neue Queues (BZ-03), beim
  Rollout auch für neue Tasks (BZ-06).
- BZ-08 im Mischbetrieb: Replay an einen 0.11-Worker verworfen (Cron-
  Replay ebenso), Replay in-flight beim Versionswechsel kann doppelt
  laufen, UI-Replays mit `max_age` können sofort ablaufen, nach einem
  UI-Move zählt das rohe `x-death`, wiederholte UI-Moves werden
  übersprungen, `route_via_dlx` nach UI-Move trägt den alten
  `x-swarmq-dead-lettered-at`.
- BZ-12: Rückstand nach dem Lauf ohne `max_age` nicht abgedeckt;
  Done-/Superseded-Marker ohne Deckel bei `max_age` über 7 d.
- BZ-01: Head-of-Line-Blocking über 1 h; innerhalb einer Stufe bis zum
  Vierfachen.
- BZ-19: Duplikate ohne Ausführungsschutz; Rollback nur auf ≥ 0.11.1;
  `reject-publish` mit `max-length`-Policy.
- BZ-10: Namensraum Pflicht bei getrennten vhosts; kein Rollback unter
  0.12 mit Namensraum; Umzug nur mit vollständigem Stopp; Leader < 0.12
  feuert alte Definitionen bis 24 h; ACL-Muster und swarmv müssen
  nachziehen; `swarmq check` zählt höchstens 5 s und im Cluster nur
  einen Knoten; `ACCESS_REFUSED` zählt für den Rücktritt.
- BZ-20: Prefetch je Consumer. BZ-21: parallele `dlq list` sehen
  Teilmengen. BZ-23: sofort publizierter Task 24 h stornierbar.
- BZ-04: Flush bei gleichzeitigem Neustart aller Prozesse und Verlust
  seit RDB-Snapshot unerkannt; Policy nur stündlich geprüft.
- KTD11: Gauge steht dauerhaft, solange eine 0.11-App am Valkey führt.
- BZ-25/05: gemischte `hard_timeout` unter einem Semaphor-Namen; 0.11-
  Erwerber verkürzen den Key.
- BZ-12/08: mit `dead_letter_ttl_s = none` Replay-Identitäten 7 d.
- Delivery-Limit per Policy nicht erkennbar und nicht unterstützt.

## 7. Bekannte Folgearbeiten (nicht Teil des RC)

- **swarmv** muss nachziehen, bevor Staging-Apps mit 0.12 dort
  beobachtet werden: die Delay-Stufen `{queue}.DQ.<stufe>` (Queue-
  Listen, Tiefen, `kind="delayed"`), den Namensraum (`<ns>:sq:…` für
  alle Keys und Kanäle), die neuen Keys (`{sched}:epoch`,
  `{sched}:handover`, `{sched}:report:known`, `{sched}:report:queues`),
  die neuen Header (`x-swarmq-dlq-gen`, `x-swarmq-xdeath-base`,
  `x-swarmq-lock-*`, `x-swarmq-unknown-since`) und das nicht
  zerstörende DLQ-Lesen; UI-Replays ohne Replay-ID laufen seit 0.12,
  `swarmq dlq retry` bleibt der empfohlene Weg. Dazu der Pin auf 0.12
  und `swarmq check` (Plan Abschnitt 8).
- **Q7-Benchmarks** für MR 10, 12 und 13 (Abschnitt 4 oben).
- Native Quorum-Prioritäten (BZ-20), P3-Befunde, `SCAN` in
  `worker_versions()` (Plan Abschnitt 8).
- `ProcessManager` mit eigenem Worker-Entry ist nicht dokumentiert
  (Doku-Befund D-7 aus der Untersuchung: ein eigener Entry muss
  `worker_slot` setzen); nur relevant, solange die Loadsuite einen
  eigenen Entry nutzt.
- Deploy-Leitfaden Schritt 0 auf `--pre` umstellen, solange nur der RC
  existiert, oder im RC-Hinweis darauf verweisen (Abschnitt 3,
  Punkt 10).
