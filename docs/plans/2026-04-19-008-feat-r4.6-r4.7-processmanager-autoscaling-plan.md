## Overview

R4.6 bringt **echtes Multiprocessing** in SwarmQ: ein Parent-Prozess
(ProcessManager) startet N Worker-Subprozesse via `spawn`-Kontext,
überwacht sie, restartet sie bei Crash mit einem Rate-Limit
(max 5 Restarts pro Stunde) und unterstützt SIGHUP-Reload via
`os.execvp()`. R4.7 setzt auf R4.6 auf: der ProcessManager passt die
Worker-Anzahl dynamisch an die Queue-Tiefe an (min..max Bounds,
Scale-Up bei voller Auslastung, Scale-Down bei Idle, Cooldown zwischen
Skalierungen).

Das bisherige CLI `swarmq worker` startet **einen** Worker in-Process.
Das bleibt als Entry-Point erhalten und dient als Worker-Subprocess-
Einstieg; neu wird `swarmq worker --processes=N` (R4.6) und
`swarmq worker --autoscale=MIN,MAX` (R4.7).

## Problem Frame

- **Ohne R4.6** skaliert ein einzelner Worker nur auf einen Python-
  Prozess und ist damit durch GIL für CPU-bound Arbeit limitiert.
  Ein Worker-Crash (segfault, oom, uncaught exception zwischen asyncio-
  Ticks) tötet den ganzen Service.
- **Ohne R4.7** muss die Worker-Anzahl statisch zur Peak-Load
  dimensioniert werden — entweder Overprovisioning (Kosten) oder
  Backlog-Aufbau bei Lastspitzen.
- **Referenz-Implementation existiert bereits** unter
  `prototypes/worker_prototype.py` (551 LoC) und dient als
  Design-Blueprint. Dieser Plan portiert die Prototyp-Struktur
  in die Production-API.

## Context & Research

### Relevant Code and Patterns

- `prototypes/worker_prototype.py` (Design-Blueprint):
  - `ProcessManager` (Zeile 315-530): Lifecycle, Monitor-Loop,
    Restart-Logik, 3-stufiger Shutdown
  - `worker_entry` (Zeile 269): Subprocess-Einstieg mit frischer
    asyncio-Loop + Logging-Setup
  - `block_signals`/`unblock_signals` (Zeile 70-90): Dramatiq-Pattern
- `src/swarmq/cli.py::_run_worker_async` (Zeile 519) — aktueller
  Single-Process-Entry, bleibt als Subprocess-Target
- `src/swarmq/worker.py::Worker.start()` — graceful shutdown via
  asyncio.Event bereits implementiert, ideal für Parent-Signal-Trigger
- `src/swarmq/broker/rabbitmq.py::purge_dead_letter_queue` (Zeile 631)
  zeigt das Pattern für `queue.message_count`-Abfrage

### Key Decisions

1. **spawn statt fork:** aiopika's Robust-Connection hält SelectorLoop-
   State, Valkey-ConnectionPool hält Sockets. Fork würde die File-
   Descriptors duplizieren und zu "leaking connection"-Warnings +
   halbtoten Sockets führen. `spawn` baut alles frisch auf —
   Start-Latenz ~0.5-1s pro Worker, akzeptabel.
2. **multiprocessing.Event als Shutdown-Signal:** in Subprocess wird
   er in einer Hintergrund-Task gepollt (0.5s); bei `set()` wird
   `asyncio.Event()` des Workers getriggert → existing graceful-
   shutdown-Flow greift.
3. **Auto-Restart-Rate-Limit 5/Stunde (roadmap) statt 5/Minute
   (prototype):** roadmap-Spec ist authoritativ; 5/min war nur
   ein Demo-Wert. Rolling-Window mit monotonic-clock.
4. **Autoscaling-Scheiben-Granularität:** +1/-1 pro Decision. Kein
   Burst-Scale. Simpler zu reasonen + testen.
5. **Scale-Down = Graceful Worker-Shutdown:** der älteste Worker
   bekommt shutdown_event gesetzt (nicht SIGTERM); drained seine
   in-flight-Tasks, Parent joint ihn, ersetzt ihn NICHT.
6. **`get_queue_depth` implementiert via passive-declare:** `queue.declare_queue(passive=True)` gibt message_count ohne bestehende Queue zu modifizieren. Wenn Queue fehlt: OK, return 0.
7. **Main/Delay-Queue-Summe als Load-Metrik:** `queue_depth_total = sum(main_count + delay_count for q in queues)`. DLQ zählt nicht zur Load.

**Goal:** Broker-API für non-destructive Queue-Tiefe. Summe aus
Main + Delay-Queue.

**Files:**
- Modify: `src/swarmq/broker/rabbitmq.py`
- Test: `tests/unit/broker/test_rabbitmq.py`

**Approach:**
```python
async def get_queue_depth(self, queue_name: str) -> int:
    """Return main + delay queue message count. 0 if queue absent."""
    try:
        channel = await self._ensure_publish_channel()
        total = 0
        for name in (queue_name, f"{queue_name}.DQ"):
            try:
                q = await channel.declare_queue(name, passive=True)
                total += int(getattr(q.declaration_result,
                                     "message_count", 0))
            except aio_pika.exceptions.ChannelNotFoundEntity:
                continue
        return total
    except Exception as exc:  # noqa: BLE001
        raise BrokerConnectionError(str(exc)) from exc
```
- `passive=True` liest ohne zu deklarieren; wenn Queue fehlt
  → `ChannelNotFoundEntity` → skip.

**Test scenarios:**
- Happy path: main=5, delay=3 → return 8
- Edge: queue absent → return 0
- Error: broker disconnected → BrokerConnectionError

- [ ] **Unit 5: R4.7 Autoscaling — Decision Loop**

**Goal:** ProcessManager passt Worker-Anzahl basierend auf
queue_depth_fn an.

**Files:**
- Modify: `src/swarmq/process_manager.py`
- Modify: `src/swarmq/cli.py` (flag `--autoscale=MIN,MAX`)
- Test: `tests/unit/test_process_manager.py`

**Approach:**
```python
SCALE_UP_THRESHOLD = 50        # pending tasks per worker
SCALE_DOWN_IDLE_S = 60.0       # Idle window before scale-down
SCALE_COOLDOWN_S = 30.0        # Between scale actions
AUTOSCALE_SAMPLE_INTERVAL = 10.0  # Queue-depth poll interval

def _autoscale_tick(self) -> None:
    if not self._autoscale or self._shutting_down:
        return
    now = time.monotonic()
    if now - self._last_scale_decision < self.SCALE_COOLDOWN_S:
        return
    min_w, max_w = self._autoscale
    depth = self._queue_depth_fn()
    active = len(self.workers)
    # Scale-up
    if depth > active * self.SCALE_UP_THRESHOLD and active < max_w:
        self._start_worker()
        self._last_scale_decision = now
        return
    # Scale-down: require sustained idle
    if depth == 0 and active > min_w:
        if self._idle_since is None:
            self._idle_since = now
        elif now - self._idle_since >= self.SCALE_DOWN_IDLE_S:
            self._scale_down_one()
            self._last_scale_decision = now
            self._idle_since = None
    else:
        self._idle_since = None
```

- `_scale_down_one`: findet den Worker mit höchstem `worker_id`,
  ruft `process.terminate()` (nicht shutdown_event — das würde ALLE
  Worker killen). → TODO: pro-worker shutdown-event. **Design-
  Iteration:** statt shared event pro-worker `process.terminate()`
  → der Worker fängt SIGTERM ab und graceful-drained (Worker hat
  bereits SIGTERM-Handler aus R2.5).
- CLI-Flag: `--autoscale=MIN,MAX` (comma-separated). Parser-Helper
  `_autoscale_range(raw) → tuple[int, int]`. Validierung: MIN ≥ 1,
  MAX > MIN.

**Test scenarios:**
- Happy path: depth=100, active=1, max=5 → scale up to 2
- Happy path: depth=0 für 60s, active=3, min=1 → scale down
- Edge: cooldown blockiert Scale-Up
- Edge: MIN=MAX → Pflicht-Scale nie (no-op)
- Edge: Depth-Sampling wirft BrokerConnectionError → log warning,
  skip tick (kein Crash)

**Verification:** `pytest tests/unit/test_process_manager.py -k autoscale`

## System-Wide Impact

- Keine Broker/Backend-Schema-Änderung
- `get_queue_depth` nutzt passive-declare → keine neuen Queues
- Worker-Subprozesse erben nichts Gefährliches vom Parent (spawn-
  Kontext)
- Backwards-Kompatibilität: ohne `--processes` / `--autoscale`
  verhält sich `swarmq worker` identisch zu R4.5 (Single-Process)

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| spawn-Startup-Latenz (~1s) auf Entwicklerlaptops auffällig | dokumentiert; nur relevant bei `--processes>1`; Default bleibt 1 |
| SIGCHLD-Reaping rennt gegen `is_alive()`-Check | prototype-getesteter Ansatz; SIGCHLD-Handler und Monitor-Loop sind idempotent |
| execvp verliert Env-Vars nicht, aber verliert Datei-Deskriptoren → Broker-Connection muss gracefully geschlossen werden vor execvp | `_shutdown_all_workers` läuft **vor** `os.execvp`; Parent hat selbst keine Broker-Connection offen |
| Autoscaling scale-down tötet einen Worker der gerade eine lange Task ausführt | `process.terminate()` löst SIGTERM aus → graceful-shutdown-Flow (R2.5) drained bis zu hard_timeout |
| Queue-Depth-Sampling pollt alle 10s den Broker → zusätzlicher Traffic | akzeptabel (10s-Rate); passive-declare ist günstig |
| Test-Flakes durch echte subprocess in CI | Unit-Tests nutzen Mocks; keine echten Subprocesses in pre-merge |
| Race zwischen Scale-Down und gleichzeitigem Crash-Restart | `_scale_down_one` setzt Flag "expected_shutdown"; `_check_dead_workers` skippt Restart wenn Flag gesetzt |

## Documentation / Operational Notes

- **Operator-Guide:** Empfehlung: `--processes` = Anzahl CPU-Cores
  (für CPU-bound Tasks) oder höher (für I/O-bound).
- **Autoscale-Empfehlung:** `--autoscale=2,10` für typische Webhook-
  Workloads. Monitoring: prometheus-Metrik `swarmq_worker_count`
  (deferred — optional in Follow-Up).
- **SIGHUP-Workflow:** `kill -HUP $(cat swarmq.pid)` triggert
  Config-Reload via execvp. Alle Worker werden neu gestartet.
