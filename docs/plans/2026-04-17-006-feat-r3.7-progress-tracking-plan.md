# feat: R3.7 — Task Progress Tracking

## Overview

Adds `Task.update_progress(current, total, message="")` as the in-task
API and `Client.get_progress(task_id)` / `Client.watch_progress(task_id)`
as the consumer-side surface. Progress is persisted as a Valkey HASH
(`sq:progress:{task_id}`) and fan-out via Valkey Pub/Sub
(`sq:progress:channel:{task_id}`). Throttling defaults to 1 update per
500ms with a forced-flush on the final update.

No new signal in v1 — Pub/Sub covers the real-time channel and
`TASK_PROGRESS` would add noise without replacing the existing
mechanism. Operators subscribe via `watch_progress` if they need push.

## Problem Frame

SwarmQ today has no mechanism for long-running tasks to surface
progress. Operators either poll task state (which only goes binary
running/done/failed) or ship their own telemetry. Celery, Dramatiq, arq
each ship some variant: Celery/Dramatiq have `update_state` with
arbitrary meta, arq has a `progress` float — none pair a first-class
client-side AsyncIterator for real-time watch.

Two primary use-cases:
- **Long ETL jobs** (hours): operator dashboard needs percent + ETA.
- **User-visible batch work** (seconds): UI progress bar via a web
  adapter.

Progress is **best-effort observability**, not a correctness feature.
Losing the occasional update is acceptable; throttling is essential
because a tight-loop task can emit tens of thousands of updates/sec.

## Requirements Trace

- **R1. `Task.update_progress(current, total, message="")`** —
  async method on the Task base class. Automatic client-side
  throttling. Origin §11.1 / aufgabe.md §6.5.
- **R2. Valkey persistence via HASH** — `sq:progress:{task_id}` with
  fields: `current`, `total`, `percent`, `message`, `updated_at`,
  `started_at`, `eta_seconds`. TTL mirrors the worker's effective
  `result_ttl` for this task so progress is cleaned up when the
  result is. Origin §11.2.
- **R3. Pub/Sub fan-out** — `PUBLISH sq:progress:channel:{task_id}
  <json>` after every successful HSET. Subscribers see updates in
  near-real-time. Origin §11.3.
- **R4. 500ms throttling** — skip updates that arrive <500ms after
  the previous one, UNLESS `current == total` (final update must
  always flush). Configurable per-task via `task_info.progress_min_interval_ms`?
  Defer to v2; hard-code 500ms for v1. Origin §11.4.
- **R5. `Client.get_progress(task_id) -> ProgressInfo | None`** —
  single HGETALL read. Returns None when no progress has been
  recorded (TTL-expired or never set).
- **R6. `Client.watch_progress(task_id) -> AsyncIterator[ProgressInfo]`** —
  yields the current HASH state first (so subscribers see the last
  known value without waiting), then streams Pub/Sub updates until
  the caller breaks. Origin §11.3.
- **R7. ETA computation** — `eta_seconds = elapsed / current *
  (total - current)` computed task-side. None when `current == 0`
  or `total <= 0`. Operator-readable, stored as str for simple
  HGETALL consumption.
- **R8. No signal emission in v1** — `TASK_PROGRESS` signal is a
  Non-Goal. Pub/Sub is the real-time channel; signals would
  duplicate at 2x the cost.
- **R9. ProgressInfo dataclass** — typed access for callers:
  `current: int`, `total: int`, `percent: float`, `message: str`,
  `updated_at: str`, `started_at: str | None`, `eta_seconds: int | None`.

## Scope Boundaries

### In-Scope

- Task-side `update_progress` with throttling.
- Valkey HASH persistence + Pub/Sub fan-out.
- Client-side `get_progress` + `watch_progress`.
- `ProgressInfo` dataclass.
- Integration with the existing worker lifecycle (task_start_time for
  ETA computation).
- Unit + integration + E2E tests.

### Non-Goals

- Progress for workflow primitives (chain/group/chord) — Phase 4 scope.
- `TASK_PROGRESS` signal in the `Signal` enum — Pub/Sub covers it.
- Configurable throttling interval per task — hard-code 500ms in v1.
- Progress persistence across worker restart — progress is ephemeral;
  a restart loses in-flight progress (accepted operator visibility gap).
- Backfilled progress for tasks enqueued before R3.7 — not applicable,
  nothing to read.
- CLI surface (`swarmq progress`) — not requested; CLI extension is
  trivial later if needed.

## Context & Research

### Relevant Code and Patterns

- **Valkey backend pattern:** `src/swarmq/backend/valkey.py` —
  `set_cancel_flag` / `is_cancelled` / `clear_cancel_flag` show the
  SET/GET/DEL-with-op_timeout discipline. Progress uses HSET+EXPIRE
  rather than plain SET, but the error-wrapping and op_timeout
  patterns are identical.
- **Pub/Sub pattern:** `ValkeyBackend.subscribe_and_wait` /
  `create_pubsub` / `publish_notification` — Client.get_result
  uses exactly this shape for the result-ready channel. R3.7
  mirrors it for progress.
- **Task lifecycle hook:** `src/swarmq/worker.py` line ~1105 —
  `task_instance = task_class()` followed by `await
  task_instance.pre_execution()` / `task_instance.run(*args,
  **kwargs)`. The worker needs to inject `task_id` + `backend`
  references into the task instance so `update_progress` can call
  the backend. Today `Task` has no back-reference; we add
  `_task_id` and `_backend` as private instance attributes set by
  the worker before `pre_execution` runs.
- **Result-TTL resolution:** `worker.py` lines ~1503-1511 — the
  cascade `task_info.result_ttl → config.result_ttl → 86400`. Progress
  TTL piggy-backs on the same resolution so operator-configured
  longer-result-TTL also gets longer-progress-TTL for free.

### Institutional Learnings

- **`swarmq-async-semaphore-deadlock-and-error-wrapping-2026-04-15.md`**:
  every new Valkey call wraps `(ValkeyError, OSError)` →
  `BackendConnectionError`. R3.7 applies the same rule.
- **Worker-pipeline ack-ordering** (worker-pipeline-stage-ack-ordering-2026-04-16.md):
  progress updates do NOT touch the message pipeline (they are pure
  Valkey side-effects between ack decisions). Rule 1 doesn't apply.
- **R3.5 Pattern 8 (header validation at ingress)**: not directly
  applicable — progress is in-process-only input.

### External References

None required — the pattern is well-established (Celery / Dramatiq /
arq) and the research doc already synthesised the design.

## Key Technical Decisions

- **Valkey HASH over JSON-in-STRING**: individual fields can be read
  without full deserialisation (operator can `HGET sq:progress:xyz
  percent` from valkey-cli). Atomic HSET per update. Trade-off:
  no nested objects — flat schema only. That matches the
  ProgressInfo fields.
- **Throttling by wall-clock, not update-count**: 500ms window is
  easier to reason about than "every Nth update" for variable-length
  loops. `asyncio.get_event_loop().time()` (monotonic) avoids system-
  clock-jump issues.
- **Force-flush on final update**: the `current == total` condition
  always bypasses throttling. Without this, a task that processes 100
  items in < 500ms would never emit a progress update.
- **ETA via linear extrapolation**: `elapsed/current * (total - current)`.
  Simple; accurate enough for coarse UX signals. More sophisticated
  models (moving average, Welford's algorithm) are over-engineered
  for v1.
- **Progress is best-effort, not durable**: Pub/Sub misses are
  tolerated; HASH-write failures are logged and swallowed so a
  transient Valkey blip cannot crash the task body. Consistent with
  the `clear_cancel_flag` discipline.
- **No signal emission**: Pub/Sub channels are per-task-id, which is
  exactly the granularity progress subscribers want. A global
  `TASK_PROGRESS` signal would require handlers to filter by
  task_id anyway. Keep the signal surface lean.
- **Progress cleared on terminal**: We do NOT explicitly DEL the
  progress HASH at the terminal. TTL cleanup suffices. Alternative:
  delete on success to free Valkey memory faster. Defer — the
  memory cost is ~200 bytes per task, which is negligible.
- **`_task_id` / `_backend` on Task instance**: set by the worker
  before `pre_execution`. Needed by `update_progress` to reach the
  backend. Existing Tasks that don't call `update_progress` pay
  nothing. Alternative: thread-local / contextvars — rejected, adds
  a non-obvious magic globally.

## Open Questions

### Resolved During Planning

- **Pub/Sub channel format**: `sq:progress:channel:{task_id}` (matches
  `sq:notify:{task_id}` for results; separate key namespace prevents
  collision).
- **TTL source**: resolved `result_ttl` at worker time, then propagated
  into `update_progress` via a task instance attribute `_result_ttl_ms`.
- **started_at initialization**: worker sets `_task_start_time =
  time.time()` before `run(*args, **kwargs)` so `update_progress`
  can compute elapsed.
- **Client.watch_progress first-yield semantics**: yield current
  HASH state on subscribe (if present), then stream. Parallel to
  `Client.get_result` pattern.

### Deferred to Implementation

- **Worker instance-vs-per-call state**: whether `_task_id` /
  `_backend` / `_task_start_time` belong on the instance
  (set once per run) or in a kwargs-injected context object.
  Instance attributes are simpler — go with that.
- **Subscribe-before-initial-read race in watch_progress**:
  subscribe first, then HGETALL, then stream Pub/Sub (same order
  as `Client.get_result`). Guarantees no missed update.

## Implementation Units

- [ ] **Unit 1: `ProgressInfo` dataclass + exceptions**

**Goal:** Typed client-side return shape.

**Requirements:** R9.

**Dependencies:** None.

**Files:**
- Create: `src/swarmq/progress.py`
- Test: `tests/unit/test_progress.py`

**Approach:**
- Frozen dataclass `ProgressInfo` with fields matching the Valkey
  HASH: `current: int`, `total: int`, `percent: float`, `message: str`,
  `updated_at: str`, `started_at: str | None`, `eta_seconds: int | None`.
- Classmethod `from_hash(raw: dict[bytes, bytes]) -> ProgressInfo`
  decodes Valkey's bytes keys/values (aio redis returns bytes) into
  typed fields. Returns None when `raw` is empty.
- Public `percent` as a computed float (already stored in HASH for
  operator HGET convenience, but dataclass owns the authoritative
  float).

**Patterns to follow:**
- `TaskInfo` in `task.py` for frozen-dataclass shape (though
  ProgressInfo is smaller + no validation logic).

**Test scenarios:**
- `from_hash({})` → None.
- `from_hash({b"current": b"42", b"total": b"100", ...})` → typed
  fields (ints where expected, floats, empty message allowed).
- Missing `eta_seconds` or empty string → None.
- Non-integer body → ValueError (pins decode contract).

**Verification:** `uv run pytest tests/unit/test_progress.py` green.

- [ ] **Unit 2: `ValkeyBackend` progress primitives**

**Goal:** Single place that touches Valkey for progress operations.

**Requirements:** R2, R3, R5.

**Dependencies:** None (builds on existing Valkey helpers).

**Files:**
- Modify: `src/swarmq/backend/valkey.py`
- Test: `tests/integration/backend/test_valkey_progress.py` (new)

**Approach:**
- `_progress_key(task_id) -> "sq:progress:{task_id}"`
- `_progress_channel(task_id) -> "sq:progress:channel:{task_id}"`
- `set_progress(task_id, fields: dict[str, str], ttl_ms: int,
  op_timeout: float | None = None) -> None`:
  - Pipeline: HSET + PEXPIRE in one round-trip (or use HSET with
    EX when Valkey supports it — check availability).
  - Wrap `(ValkeyError, OSError)` → `BackendConnectionError`.
- `get_progress(task_id, op_timeout) -> dict[bytes, bytes] | None`:
  - HGETALL. Returns None when empty (key absent or TTL-expired).
  - Caller decodes via `ProgressInfo.from_hash`.
- `publish_progress(task_id, payload: bytes) -> None`:
  - PUBLISH to channel. Failures logged + swallowed (same as
    `publish_notification`).
- Pub/Sub subscription:
  - Reuse existing `create_pubsub` + `subscribe_and_wait` patterns.
  - `subscribe_progress(task_id) -> (pubsub, channel)` helper or
    defer to Client (see Unit 4).

**Patterns to follow:**
- `set_cancel_flag` (valkey.py) for op_timeout + error-wrap.
- `publish_notification` (valkey.py) for swallow-on-fail pattern.
- `create_pubsub` for subscriber construction.

**Test scenarios:**
- set_progress writes all fields, HGETALL returns them.
- TTL: after ttl_ms passes, HGETALL returns empty.
- publish_progress: subscribe + publish → receiver sees payload.
- Multiple consecutive set_progress calls: last write wins.
- get_progress on missing key → None (not KeyError).
- set_progress on closed connection → BackendConnectionError.

**Verification:** `uv run pytest tests/integration/backend/test_valkey_progress.py`
green against dev stack.

**Execution note:** Test-first. Pub/Sub timing is subtle; pin the
"subscribe-then-publish-then-receive" sequence before writing the
Client layer.

- [ ] **Unit 3: `Task.update_progress` + worker integration**

**Goal:** In-task API with throttling; worker injects needed state.

**Requirements:** R1, R4, R7.

**Dependencies:** Unit 2.

**Files:**
- Modify: `src/swarmq/task.py`
- Modify: `src/swarmq/worker.py`
- Test: `tests/unit/test_task.py`, `tests/unit/test_worker.py`

**Approach:**
- On `Task`:
  - Class-level constant `_PROGRESS_MIN_INTERVAL_S = 0.5`.
  - Instance attributes initialised in `__init__`:
    `_task_id: str | None = None`,
    `_backend: ValkeyBackend | None = None`,
    `_task_start_time: float | None = None`,
    `_result_ttl_ms: int = 86_400_000`,
    `_last_progress_update: float = 0.0`.
  - New async method `update_progress(current, total, message="")`:
    - No-op when `_backend is None` (task is being unit-tested without
      a worker wiring).
    - Throttle: skip if `now - _last_progress_update <
      _PROGRESS_MIN_INTERVAL_S` AND `current < total`.
    - Compute `percent`, `elapsed`, `eta_seconds`.
    - Build fields dict, call `backend.set_progress`.
    - Build JSON, call `backend.publish_progress`.
    - Set `_last_progress_update = now`.
    - Wrap broad `Exception` → log warning + swallow. Progress is
      best-effort; a Valkey blip must not abort the task body.
- In `Worker._handle_message` around the existing
  `task_instance = task_class()` call (~line 1108):
  - After construction, before `pre_execution()`:
    ```python
    task_instance._task_id = task_id
    task_instance._backend = self._backend
    task_instance._task_start_time = time.time()
    task_instance._result_ttl_ms = resolved_result_ttl * 1000
    ```
  - resolve `resolved_result_ttl` from the existing TTL cascade
    (pull the same 3 lines that line ~1503-1511 already execute;
    factor out a helper if readability suffers).

**Patterns to follow:**
- Existing `Task` lifecycle shape in `task.py`.
- Worker's cancel-monitor for the "best-effort backend call +
  swallow" pattern.

**Test scenarios (Task unit):**
- `update_progress(10, 100, "half")` on a task with no backend →
  no raise, no-op.
- With mocked backend: first call fires set+publish; second call
  within 500ms is skipped; third call after >500ms fires again.
- `current == total` bypasses throttling.
- eta_seconds = None when current == 0.
- eta_seconds > 0 when progress is non-trivial; correctness check.
- Backend raise → no propagation, warning logged.

**Test scenarios (Worker integration):**
- Registered Task calls update_progress in run() → backend's
  set_progress / publish_progress are awaited with correct args
  (mock the backend).
- `_task_start_time` set before run() called.
- `_result_ttl_ms` matches the worker's TTL cascade (task → config
  → 86400).

**Verification:** `uv run pytest tests/unit/test_task.py tests/unit/test_worker.py -k progress`
green.

- [ ] **Unit 4: `Client.get_progress` + `Client.watch_progress`**

**Goal:** Consumer-side API for polling + streaming.

**Requirements:** R5, R6.

**Dependencies:** Unit 1 (ProgressInfo), Unit 2 (backend primitives).

**Files:**
- Modify: `src/swarmq/client.py`
- Test: `tests/unit/test_client.py`, `tests/integration/test_client_progress.py` (new)

**Approach:**
- `Client.get_progress(task_id: str) -> ProgressInfo | None`:
  - `raw = await backend.get_progress(task_id)` — HGETALL.
  - Return `None` when empty.
  - Decode via `ProgressInfo.from_hash(raw)`.
- `Client.watch_progress(task_id: str) -> AsyncIterator[ProgressInfo]`:
  - Subscribe to channel FIRST (avoid missing an update between
    initial read and subscribe).
  - HGETALL to surface the last known state; yield it if present.
  - Loop: `pubsub.get_message` with small timeout, decode JSON,
    yield ProgressInfo. Break when caller breaks.
  - Cleanup (`unsubscribe` + `aclose`) in finally.
  - Pattern mirrors `Client.get_result`'s subscribe-then-poll flow.

**Patterns to follow:**
- `Client.get_result` (client.py) for the subscribe-first + initial-
  check ordering.

**Test scenarios (unit, mocked backend):**
- `get_progress` with mocked HGETALL None → returns None.
- `get_progress` with mocked HGETALL dict → returns typed ProgressInfo.
- `watch_progress` cleanup on caller-break (subscribe + unsubscribe
  exactly once).

**Test scenarios (integration, real Valkey):**
- set_progress + get_progress round-trip.
- watch_progress yields the initial state + subsequent updates.
- watch_progress returns nothing when task_id has no progress.
- watch_progress receives multiple updates in order.

## System-Wide Impact

- **Client API:** new `get_progress` + `watch_progress` methods.
  Additive; no existing API change.
- **Task base class:** new `update_progress` method; new private
  instance attrs set by worker. Backward-compatible — pre-R3.7
  tasks that never call `update_progress` are unaffected.
- **ValkeyBackend:** three new methods (set_progress, get_progress,
  publish_progress). Additive.
- **No Broker changes.** Progress is pure Valkey.
- **No Scheduler changes.** Scheduler-fired tasks use the same
  worker path, so they inherit progress automatically.
- **No new Signal enum member.** Explicit v1 non-goal.
- **TTL on progress HASH** uses the same resolved value as
  `result_ttl`, so operator-tuned result retention also tunes
  progress retention for free.

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| Progress-storm (tight-loop task publishing thousands of updates/sec) | Task-side 500ms throttling; final-flush always honoured. |
| Pub/Sub miss when subscriber starts after the task's last update | watch_progress does HGETALL on subscribe → yields the last known state, bridging the gap. |
| Pre-R3.7 tasks that accidentally reference `_backend` / `_task_id` as user data | Private `_` prefix + no documented user access; any pre-existing task setting these names collides, but that risk is vanishingly small. |
| Valkey outage mid-task: HSET fails | Broad except + log warning; task body continues. Progress lost for that update, not fatal. |
| Client `watch_progress` outlives the task's result TTL | Progress HASH is gone; pubsub still subscribed but no more publishes. Caller breaks when done. Documented. |
| ETA inaccurate for non-linear progress | Accepted limitation; documented in the `update_progress` docstring. |
| Worker restart loses in-flight progress | Accepted — progress is ephemeral; TTL expires the stale HASH within `result_ttl` after the worker died. |
