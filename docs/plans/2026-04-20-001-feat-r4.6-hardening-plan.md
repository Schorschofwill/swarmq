## Problem Frame

Die aktuelle ProcessManager-Implementierung hat fünf konkrete
Schwächen:

1. **Retry-Storm bei kaputtem User-Modul:** Wenn `import_module(args.module)`
   im Subprocess scheitert (ImportError beim Startup), crasht der
   Subprocess sofort. Der Supervisor restartet ihn 5x in Sekunden und
   das Slot ist dann dauerhaft tot — obwohl das Problem deterministisch
   ist (kein transient crash).

2. **11-Parameter Signatur-Drift:** `worker_subprocess_entry` nimmt 11
   positional Parameter. Drei Stellen (Funktion, `worker_args`-Tuple,
   `argparse.Namespace`-Rekonstruktion) müssen synchron bleiben —
   jede neue CLI-Flag ist ein 3-Site-Edit mit silent-Mismatch-Risiko.

3. **`--module`-Format-Guard fehlt:** Argparse akzeptiert beliebige
   Strings; `importlib.import_module` führt Top-Level-Code unbesehen
   aus. Keine Defense-in-Depth gegen Tippfehler oder falsch geroutete
   Pfade.

4. **Orphan-Child bei execvp:** `os.execvp` nach SIGHUP ersetzt den
   Parent-Prozess-Image; wenn ein Kind beim Execvp noch lebt (drain-
   timeout überschritten + SIGKILL verpasst), wird es ein Zombie an
   init/systemd statt sauber geschlossen zu werden.

5. **Crash-während-Idle Spawn/Kill-Churn:** Im Autoscale-Idle
   spawnt der Supervisor einen Replacement-Worker nach einem Crash
   und killt ihn unmittelbar darauf via Scale-Down. Netto: unnötiger
   Prozess-Churn + verwirrende Logs.

6. **sys.argv-Replay unvalidiert:** Bei SIGHUP-Reload wird `sys.argv`
   byte-für-byte an `os.execvp` weitergereicht. Dokumentation zur
   Trust-Grenze fehlt — ein Operator muss wissen, dass Launch-Command-
   Injection das Reload-Verhalten kompromittiert.

## Key Decisions

1. **WorkerConfig als frozen dataclass** in `process_manager.py` (nicht
   in `config.py` — Scope-Creep vermeiden, es ist kein User-facing
   Config). Pickle-safety wird per `__post_init__`-isinstance-Check
   zur Laufzeit erzwungen (nicht nur per Docstring-Policy); `queues`
   ist `tuple[str, ...]` statt `list[str]` um das frozen-Versprechen
   gegen interne Mutation zu halten.

2. **Fast-fail bei ImportError:** Pre-flight `importlib.util.find_spec`
   im PARENT vor dem ersten Spawn. Schlägt das fehl → `ConfigurationError`
   vor dem supervisor.run(), kein Restart-Loop. Läuft nur einmal
   (beim Start), kein Per-Spawn-Overhead.

3. **dotted-identifier Regex:** `re.compile(r"^[a-zA-Z_]\w*(\.[a-zA-Z_]\w*)*$")`
   als Argparse-Validator. Lehnt Shell-Metachars, Pfad-Trenner und
   leere Segmente ab. Liberal genug für reale Task-Module-Namen,
   strikt genug gegen offensichtlichen Unsinn.

4. **execvp-Guard:** Nach `_shutdown_all_workers` + `_collect_zombies`
   zählen wir `sum(1 for w in self.workers.values() if w.process.is_alive())`.
   Wenn > 0 → **WARNING-Log** (mit Operator-Hint) + **return 0**
   (NICHT exit 1 — sonst würde systemd/k8s den Parent neu starten
   und den Guard infinit re-loopen). Operator kann SIGHUP nochmal
   senden wenn Child tot ist; bei D-State-Child braucht es Host-
   Level-Recovery. Dokumentiert im Cookbook.

5. **Scale-Down-Min-Age:** Worker braucht mindestens `SCALE_MIN_AGE_S`
   (30s) zwischen Spawn und Scale-Down-Eligibility. Der bereits
   vorhandene Cooldown schützt den Parent nicht vor genau diesem Bug,
   weil der Cooldown nur scale-Actions zählt, nicht Spawn-Actions.

6. **SIGHUP-argv-Snapshot als Code-Fix:** `sys.argv` wird bei
   `ProcessManager.__init__` in `self._startup_argv` eingefroren;
   `os.execvp` nutzt diesen Snapshot statt live `sys.argv`. Schließt
   in-Process-Mutation (2-Zeilen-Fix, schlägt 0 Kosten). Doku-Ergänzung
   (Unit 8) framed das als "by design", nicht als Mitigation einer
   offenen Schwäche.

**Approach:**
```python
import dataclasses

@dataclasses.dataclass(frozen=True)
class WorkerConfig:
    module: str
    queues: tuple[str, ...]          # tuple, nicht list — konsistent mit frozen
    concurrency: int
    log_level: str
    log_format: str
    burst: bool
    burst_idle_timeout: float
    priorities: bool
    metrics_port: int | None
    health_port: int | None

    def __post_init__(self) -> None:
        # Pickle-Boundary-Invariante per Runtime-Check erzwingen —
        # docstring-only policy ist nicht enforceable.
        _ALLOWED = (str, int, float, bool, tuple, type(None))
        for f in dataclasses.fields(self):
            value = getattr(self, f.name)
            if not isinstance(value, _ALLOWED):
                raise TypeError(
                    f"WorkerConfig.{f.name} must be pickle-safe "
                    f"(got {type(value).__name__})"
                )
        if self.log_level not in ("DEBUG", "INFO", "WARNING", "ERROR"):
            raise ValueError(f"invalid log_level: {self.log_level}")


def worker_subprocess_entry(
    worker_id: int,
    shutdown_event,
    cfg: WorkerConfig,
) -> None:
    # Rebuild argparse.Namespace from cfg — only one site now.
    # asdict honours tuple-fields (converts to list) — we re-wrap
    # queues below because Namespace callers may expect list identity.
    kwargs = dataclasses.asdict(cfg)
    kwargs["queues"] = list(kwargs["queues"])
    ns = argparse.Namespace(**kwargs)
    ...
```
- `run_multi_process_worker` baut `WorkerConfig(queues=tuple(args.queues), ...)`
  einmal, reicht es als `worker_args=(cfg,)` durch.
- `tuple[str, ...]` statt `list[str]`: frozen-dataclass verspricht
  immutability — list-Feld würde dieses Versprechen verletzen (Liste
  ist intern mutierbar). tuple ist pickle-safe und hashable.
- `__post_init__` erzwingt die Pickle-Boundary-Invariante zur Laufzeit
  statt rein in der docstring — schließt den Gap für zukünftige
  programmatische Caller.

**Test scenarios:**
- Happy path: WorkerConfig roundtripped durch `pickle.dumps/loads`
  (expliziter Test für die Pickle-Boundary — Verifikation dass der
  Refactor nicht silent bricht)
- `WorkerConfig(queues=["a"])`-Konstruktion mit list-Argument raist
  `TypeError` (isinstance-Check)
- `WorkerConfig(log_level="TRACE")` raist `ValueError`
- Neue CLI-Flag hinzufügen: nur 1 Site (WorkerConfig-Feld + Construction
  in run_multi_process_worker) statt bisher 3

tests/unit/test_cli_multiprocess.py` grün. Keine Regressions.

- [x] **Unit 2: ImportError Fast-Fail (Pre-Flight-Check)**

**Goal:** Kaputtes User-Modul produziert einen einzelnen
ConfigurationError im Parent, nicht einen 5-Restart-Storm.

**Files:**
- Modify: `src/swarmq/process_manager.py`
  (`run_multi_process_worker` pre-flight)
- Test: `tests/unit/test_cli_multiprocess.py`

**Approach:**
```python
import importlib.util
from swarmq.exceptions import ConfigurationError

def _validate_module_importable(module: str) -> None:
    """Raise ConfigurationError if ``module`` cannot be resolved.
    Runs in the parent before the supervisor starts, so a typo
    or a filesystem-level missing module fails once with a clear
    error instead of looping through 5 subprocess restarts.
    """
    try:
        spec = importlib.util.find_spec(module)
    except (ModuleNotFoundError, ValueError) as exc:
        raise ConfigurationError(
            f"--module {module!r} cannot be imported: {exc}",
        ) from exc
    # spec.origin is None für Namespace-Packages (__init__.py fehlt) —
    # find_spec liefert einen spec, aber import_module wird scheitern.
    if spec is None or spec.origin is None:
        raise ConfigurationError(
            f"--module {module!r} resolves to no loadable spec — "
            "check spelling, PYTHONPATH, and __init__.py presence",
        )
```
- `ConfigurationError` wird top-level in `process_manager.py`
  importiert (nicht lazy), weil der Aufruf vor dem Supervisor-Start
  passiert — Konsistenz mit dem bestehenden lazy-Import in
  `run_multi_process_worker` aufheben.
- Aufruf in `run_multi_process_worker` direkt nach env-var-checks,
  vor ProcessManager-Konstruktion.

**Known Limitations (explizite Liste — find_spec ist kein Sandbox):**
Der Pre-Flight fängt **nur** "Modul kann nicht resolvt werden". Die
folgenden Szenarien produzieren weiterhin den 5-Restart-Storm im
Subprocess (aber nach find_spec-Success):

- **Fehlende transitive Dependency**: `tasks.py` existiert,
  importiert aber `from missing_dep import X` → find_spec succeeds,
  import_module raised im Subprocess
- **Kaputte C-Extension / ABI-Mismatch**: `.so` existiert, dlopen
  schlägt im Subprocess fehl
- **Env-abhängige Imports**: Top-Level `if os.environ.get(...)` mit
  Parent-vs-Child-Env-Divergenz
- **Zirkuläre Imports**: find_spec kann partiell succeed
- **PYTHONPATH-Shadowing**: Namespace-Package-Auflösung kann im
  Parent anders ausgehen als im Child

Für alle diese Fälle greift die Unit-3-Restart-Limit-Kappung (5/h
rolling-window). Der Changelog-Eintrag + die Cookbook-Seite dokumentieren
das explizit: "Pre-flight catches module-not-found only. A module that
exists but fails to load (missing transitive dep, broken C ext, env-
conditional import) will still trigger the subprocess restart loop —
use `swarmq inspect --module myapp.tasks` to diagnose before starting
workers."

**Test scenarios:**
- Happy path: `"swarmq.cli"` → kein Raise
- Invalid: `"does.not.exist"` → ConfigurationError
- Malformed: `"with spaces"` → ConfigurationError via ValueError
- Namespace-package edge: Modul ohne `__init__.py` → ConfigurationError
  (spec vorhanden, aber `spec.origin is None`)
- Happy-but-subprocess-fails: Modul mit missing transitive dep →
  find_spec succeeds (dokumentiert, kein Test — Subprocess-Restart-Limit
  greift)

**Verification:** `pytest tests/unit/test_cli_multiprocess.py -k import`
grün.

- [x] **Unit 3: Dotted-Identifier Argparse-Validator**

**Goal:** `--module` lehnt offensichtlichen Unsinn ab, bevor
importlib überhaupt gerufen wird.

**Files:**
- Modify: `src/swarmq/cli.py` (neuer Validator-Helper)
- Test: `tests/unit/test_cli.py` oder `test_cli_multiprocess.py`

**Approach:**
```python
import re

# Python-3-Identifier-Grammar (PEP 3131-compliant): unterstützt
# Unicode-Letter/Digit-Zeichen wie in `ast.parse("café = 1")`.
# `\w` im UNICODE-Modus matched [a-zA-Z0-9_] plus alle Python-
# validen Unicode-Letter/Digits. `[^\W\d]` ist "word-char, aber
# kein Digit" — also der zulässige Start eines Identifiers.
_DOTTED_IDENTIFIER_RE = re.compile(
    r"^[^\W\d]\w*(\.[^\W\d]\w*)*$",
    re.UNICODE,
)


def _dotted_module_name(raw: str) -> str:
    if not _DOTTED_IDENTIFIER_RE.match(raw):
        raise argparse.ArgumentTypeError(
            f"--module {raw!r} is not a dotted Python identifier "
            "(expected: package.module.submodule)"
        )
    return raw
```
- Anwendung auf `worker.add_argument("--module", type=_dotted_module_name)`
  UND `inspect.add_argument("--module", type=_dotted_module_name)`
  (separater Checkbox-Punkt, damit nicht nur einer geändert wird).
- Unit 2 (Pre-Flight) ergänzt das: Format-Check first, Resolvability-
  Check second.

**Security-Scope (explizit):** Der Regex blockt Shell-Metazeichen,
Pfad-Trenner und offensichtlich nicht-importierbare Inputs. Er ist
**kein** Code-Execution-Guard — jeder regex-konforme Name wird von
`importlib.import_module` unbesehen ausgeführt. Die eigentliche
Trust-Grenze ist der argv-Snapshot (Unit 6) + PYTHONPATH-Kontrolle
des Operators (Unit 7 docs).

**Test scenarios:**
- Happy: `myapp.tasks` → accepted
- Happy: `_private.worker._impl` → accepted
- Happy: `café.tasks` (PEP 3131 Unicode) → accepted
- Happy: `日本.tasks` → accepted
- Reject: `my-app.tasks` (hyphen) → ArgumentTypeError
- Reject: `/etc/passwd` → ArgumentTypeError
- Reject: `myapp..tasks` (leerer segment) → ArgumentTypeError
- Reject: `123.main` (leading digit) → ArgumentTypeError
- Reject: `.hidden` (leading dot) → ArgumentTypeError
- `inspect --module`-Pfad separat getestet (regression-guard)

**Verification:** `pytest tests/unit/test_cli.py -k dotted_module`
oder neue Datei. Beide Subparser (worker + inspect) abgedeckt.

- [x] **Unit 4: execvp-Orphan-Guard** `[R5.3 Prerequisite]`

**Goal:** SIGHUP-Reload wird nicht ausgeführt, wenn Kinder noch
leben. Parent exit-0 mit WARNING-Log + Operator-Hint.

**Files:**
- Modify: `src/swarmq/process_manager.py`
- Test: `tests/unit/test_process_manager.py`

**Approach:**
```python
def run(self) -> int:
    ...
    try:
        retcode = self._monitor_loop()
    finally:
        self._shutdown_all_workers()
        self._collect_zombies()

    if self._reload_requested:
        alive = [
            w for w in self.workers.values() if w.process.is_alive()
        ]
        if alive:
            logger.warning(
                "reload_aborted_alive_children",
                alive_count=len(alive),
                alive_pids=[w.process.pid for w in alive],
                hint=(
                    "re-send SIGHUP once all workers have exited; "
                    "a D-state process (uninterruptible kernel wait) "
                    "may require host-level intervention"
                ),
            )
            return 0  # Parent exit clean — systemd wird NICHT neu starten
        try:
            logger.info("process_manager_reload_execvp")
            os.execvp(sys.executable, [sys.executable] + sys.argv)
        except OSError as exc:
            logger.error("reload_execvp_failed", error=str(exc))
            return 1
    return retcode
```
- **Design-Entscheidung** (ce-review coherence F-03): WARNING + exit 0,
  NICHT ERROR + exit 1. Begründung: Parent hat sauber alle Phasen
  durchlaufen; ein Prozess-Supervisor (systemd, k8s) soll NICHT neu
  starten bis der Operator die Ursache adressiert hat. ERROR-exit-1
  würde einen Neu-Start triggern, der den Guard erneut fest-loopen
  würde.
- **D-State-Limitation** (ce-review adversarial #4): Wenn das
  überlebende Child in uninterruptible kernel wait steckt (NFS-Stall,
  dying disk), hilft auch wiederholter SIGKILL nicht. Der Log-Hint
  macht das explizit; wirkliche Recovery braucht Host-Level-Eingriff.
  Dokumentiert im Cookbook-Abschnitt "Reload-Pathologies".
- `OSError` um `os.execvp` — wenn `sys.executable` nicht ausführbar
  ist, saubere Fehler-Log statt raw traceback.

**Test scenarios:**
- Happy: `_reload_requested=True`, keine Alive-Workers → execvp
  gerufen (bestehender Test deckt ab — `self.workers={}` → `alive=[]`)
- **Guard (neu):** `_reload_requested=True`, 1 Alive-Worker → execvp
  NICHT gerufen, WARNING-Log emittiert, Return 0
- **OSError-Pfad (neu):** execvp wirft OSError → `reload_execvp_failed`
  ERROR-Log, Return 1

**Verification:** `pytest tests/unit/test_process_manager.py -k reload`
grün (2 neue Tests; bestehender `test_run_triggers_execvp_on_reload`
testet implizit den empty-workers Branch).

```python
    def __init__(self, ..., shutdown_grace_s=None):
        ...
        # Freeze argv at supervisor start. SIGHUP-Reload uses this
        # snapshot so in-process mutation (buggy third-party lib,
        # compromised user module rewriting sys.argv) cannot
        # influence the re-exec vector (ce-review SEC-01).
        self._startup_argv: list[str] = list(sys.argv)

    def run(self) -> int:
        ...
        if self._reload_requested:
            ...
            os.execvp(sys.executable, [sys.executable] + self._startup_argv)
```
- 2-Zeilen-Change gegenüber dem bisherigen `[sys.executable] + sys.argv`.
- Das bewahrt argv-Mutation durch andere Prozesse nicht (das ist
  auf POSIX ohnehin nicht möglich — `sys.argv` ist eine Python-
  List-Kopie aus `PyMain_Init`), aber es schützt vor in-Prozess
  Re-Binding via `sys.argv[...] = ...`.

**Test scenarios:**
- Happy: `sys.argv` wird in `__init__` in `_startup_argv` eingefroren
- Guard (neu): nach `__init__` wird `sys.argv[0] = "mutated"` gesetzt;
  `pm._startup_argv[0]` bleibt unverändert
- Smoke: `run()` mit `_reload_requested=True` ruft `os.execvp` mit
  `_startup_argv`, nicht `sys.argv`

**Verification:** `pytest tests/unit/test_process_manager.py -k argv`
grün.

- [x] **Unit 7: cli-Import-Inversion entschärfen (M-3)**

**Goal:** `process_manager.py::worker_subprocess_entry` importiert
`swarmq.cli._run_worker_async` (private Symbol). Nach Rename von
`_run_worker_async` → `run_worker_async` wird der Import statisch
am Modul-Top statt im Subprocess-Entry lazy — jede `cli.py`-Änderung,
die das Symbol bricht, wird sofort zum Import-Error im Parent statt
zum laufzeit-sichtbaren Subprocess-Crash.

**Files:**
- Modify: `src/swarmq/cli.py` (Rename `_run_worker_async` →
  `run_worker_async`; Call-Site in `main()` anpassen)
- Modify: `src/swarmq/process_manager.py` (Top-Level-Import
  ergänzen; lazy-Import im Subprocess-Entry entfernen)
- Test: kein neuer Test — bestehende Tests stellen die Call-Site
  sicher

**Approach:**
- `cli.py`: `async def _run_worker_async(...)` → `async def run_worker_async(...)`.
  In `main()` wird `_run_worker_async` an 1 Stelle gerufen — umbenennen.
- `process_manager.py`: Top-Level `from swarmq.cli import run_worker_async`
  entfernt den lazy-Import aus `worker_subprocess_entry`. Spawn-
  Safety bleibt erhalten (spawn re-importiert die Module fresh,
  kein ForkServer-Pickle-Problem).
- **Kein architektonisches Refactoring** (cli-importiert-pm statt
  umgekehrt) — das wäre Scope-Creep. Der Fix konvertiert nur das
  runtime-unsichtbare Private-Symbol in eine statische Public-

**Test scenarios:**
- Alle bestehenden Tests laufen unverändert grün (die Call-Sites
  greifen das Symbol über den neuen Namen — sind drei Stellen,
  einmal gerenamed)
- Regression-Guard: Wenn jemand später `run_worker_async` wieder
  entfernt oder rename, failt der Import in `process_manager.py`
  beim PARENT-Start, nicht bei einem SPAWN-Aufruf Stunden später

**Verification:** `pytest tests/unit/` grün. `grep -rn _run_worker_async
src/swarmq/` liefert 0 Treffer nach dem Rename.

## System-Wide Impact

- Keine Broker/Backend-Schema-Änderung
- Keine CLI-Breaking-Changes (Validator-Regex ist inklusiv für
  alle bisher gültigen Module-Namen)
- Subprocess-Entry-Signatur IST Breaking für direkte Aufrufer von
  `worker_subprocess_entry` — dort ist aber niemand außerhalb von
  `run_multi_process_worker`

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| `find_spec` kann bei Namespace-Packages trügen | Dokumentiert; Subprocess-Crash-Loop bleibt als Sicherheitsnetz |
| Strenger Dotted-Regex lehnt exotische aber gültige Modulnamen ab (z.B. Unicode-Identifier in PEP 3131) | Regex bewusst ASCII-only — PEP 3131 wird selten genutzt und aktiviert CVE-Klassen (Homoglyph). Wenn User das braucht: opt-out via Flag in Follow-Up |
| `WorkerConfig` als Pickle-Target könnte Probleme machen wenn später nicht-primitive Felder hinzukommen | Pickle-safety ist Subprocess-Boundary-Invariante — enforce via Frozen-dataclass + primitive-types-only-Policy im Docstring |
| execvp-Guard verwandelt "manchmal Reload" in "bleibt stehen" bei langsamen Drains | Konservativer Default. Operator kann zweites SIGHUP senden nachdem der letzte Worker tot ist. Dokumentiert |
| SCALE_MIN_AGE_S=30s verlängert die Zeit bis Scale-Down-Reaktion | Bewusster Trade-off. 30s ist kürzer als SCALE_DOWN_IDLE_S=60s, beeinflusst Steady-State nicht |
